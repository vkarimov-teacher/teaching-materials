How DNS Works

The Domain Name System — resolution flow, UDP vs TCP transport, resource records, common attacks, and the mechanisms that defend it.

1 · Basics 2 · Resolution 3 · UDP & TCP 4 · Records 5 · Attacks 6 · Security

01 What DNS Is

DNS is the internet's distributed directory. It translates human-readable names like www.example.com into IP addresses like 93.184.216.34 (and back), so machines can route traffic while people use names.

The name hierarchy

Names are read right-to-left, from most general to most specific. A trailing dot marks the root.

# www.example.com.
.              → root
com.           → TLD
example.com.   → authoritative zone
www.example.com. → host / FQDN

The four players

Stub resolverThe client OS library that asks the question.
RecursiveThe resolver that does the legwork and caches answers.
Root / TLDReferral servers that point toward the right zone.
AuthoritativeHolds the real records for a zone.

02 The Resolution Flow

A recursive resolver walks the hierarchy on the client's behalf. Each server either answers or refers it one step closer. Answers are cached along the way, honoring each record's TTL.

1
Client → Recursive resolver
"What is the A record for www.example.com?" The stub resolver sends a recursive query.
2
Resolver → Root server
Root doesn't know the answer but refers: "ask the .com TLD servers."
3
Resolver → TLD server (.com)
TLD refers: "ask the authoritative name servers for example.com" (NS + glue records).
4
Resolver → Authoritative server
Returns the authoritative answer: www.example.com A 93.184.216.34.
5
Resolver → Client
Resolver caches the record for its TTL and returns the answer to the stub resolver.
Recursive vs iterative: the client's query is recursive ("get me the final answer"). The resolver's queries to root/TLD/authoritative are iterative ("give me your best referral"). Caching is what keeps step 2–4 from happening on every lookup.

Message anatomy

Every DNS message — query or response — shares one 12-byte header followed by four sections.

# DNS header (12 bytes)
ID        16-bit transaction ID  ← must match in the reply
Flags     QR, Opcode, AA, TC, RD, RA, RCODE
QDCOUNT   # questions
ANCOUNT   # answer RRs
NSCOUNT   # authority RRs
ARCOUNT   # additional RRs
# Sections: Question | Answer | Authority | Additional

TC The TC (truncation) flag is the hinge between transport modes — see the next section.

03 DNS over UDP and TCP

DNS uses port 53 on both UDP and TCP. UDP is the default because it's fast and connectionless; TCP is the fallback when a single datagram isn't enough or reliability is required.

AspectUDP (default)TCP (fallback)
Setup costNone — one packet out, one back3-way handshake first
SpeedLow latency, ideal for small queriesHigher latency
ReliabilityNo delivery guaranteeOrdered, acknowledged delivery
Size limit512 B classic; larger via EDNS0Effectively unbounded (2-byte length prefix)
Spoofing riskHigher — easy to forge sourceLower — handshake resists blind spoofing

When DNS switches to TCP

1Truncation. If a UDP response exceeds the client's buffer, the server sets the TC flag. The client retries the same query over TCP to get the full answer.
2Zone transfers. AXFR (full) and IXFR (incremental) between authoritative servers always use TCP — the payload is large and must be reliable.
3Large responses. DNSSEC signatures, big RRSETs, and many-record answers routinely exceed UDP limits.

EDNS0 — extending UDP

Classic DNS capped UDP payloads at 512 bytes. EDNS0 (via an OPT pseudo-record) lets a client advertise a larger buffer, commonly 1232–4096 bytes, so big responses can still ride UDP and avoid the TCP round-trip. Oversized EDNS buffers also enable amplification attacks — noted in section 5.

Encrypted transports: plain DNS on port 53 is cleartext. DoT (DNS over TLS, port 853) and DoH (DNS over HTTPS, port 443) wrap queries in TLS for confidentiality. DoQ (DNS over QUIC) does the same over UDP/QUIC. These protect privacy on the wire but are distinct from DNSSEC, which protects integrity.

05 DNS Attacks

DNS is trusted by everything and, in its classic form, authenticates nothing. That makes it a rich target for spoofing, redirection, denial-of-service, and covert channels.

Cache poisoning / spoofing

An attacker races to inject a forged response into a recursive resolver's cache. If the fake reply matches the query's transaction ID, source port, and question before the real answer arrives, the resolver caches the malicious record and serves it to every client until TTL expiry.

Kaminsky attack

A 2008 refinement of cache poisoning. By querying random non-existent subdomains and forging referrals for the parent zone's NS records, the attacker gets unlimited retries and can hijack an entire domain rather than a single hostname. It's why source-port randomization became mandatory.

DNS amplification (DDoS)

A reflection attack: the attacker spoofs the victim's IP as the source of small queries to open resolvers, which return much larger responses (EDNS0, ANY, DNSSEC). A tiny request yields a large reply aimed at the victim — amplification factors of 50× or more.

DNS tunneling

Data is smuggled inside DNS queries/responses (encoded in subdomain labels or TXT records) to exfiltrate data or run C2 over a channel that firewalls rarely block. Detected by anomalous query volume, entropy, and record types to a single domain.

Hijacking & rebinding

DNS hijacking alters resolver settings or registrar/zone records to redirect traffic. DNS rebinding abuses short TTLs to make a browser resolve a name first to the attacker, then to an internal IP — bypassing same-origin defenses to reach internal services.

Subdomain takeover & NXDOMAIN abuse

A dangling CNAME pointing to a deprovisioned cloud resource lets an attacker claim it and serve content under your domain. NXDOMAIN / random-subdomain (water torture) floods resolvers with junk names to exhaust authoritative servers.

06 DNS Security Mechanisms

Defenses split into three goals: integrity (is the answer authentic?), confidentiality (who can read my queries?), and availability / hygiene (resilience and abuse prevention).

DNSSEC — integrity

DNSSEC signs records with public-key crypto. Each RRset carries an RRSIG; DNSKEY holds the zone's keys; and a DS record in the parent zone hashes the child's key, forming a chain of trust from the root down. A validating resolver rejects any answer whose signature doesn't verify — defeating cache poisoning and spoofing.

Note: DNSSEC provides authenticity and integrity, not confidentiality. Queries and answers are still cleartext. NSEC/NSEC3 give signed proof that a name does not exist.

Query hardening — anti-spoofing

Port random.Randomized source ports add ~16 bits of entropy against blind forgery.
0x20 encoding.Randomizing the case of query names adds unpredictability the attacker must also match.
TXID entropy.Cryptographically random transaction IDs, not sequential.

Encrypted transport — confidentiality

DoT (853), DoH (443), and DoQ wrap DNS in TLS/QUIC so on-path observers can't read or tamper with queries. Complements DNSSEC rather than replacing it — one protects the wire, the other protects the data.

Availability & abuse control

Response Rate Limiting (RRL) blunts amplification. Disabling open recursion, restricting ANY, and BCP 38 ingress filtering cut reflection. Anycast and redundant NS spread load and survive DDoS. Restrict AXFR to trusted peers (TSIG).

Authenticated management

TSIG (shared-key) and SIG(0) authenticate zone transfers and dynamic updates. CAA records limit which CAs can issue certificates for your domain. Registrar lock and DNSSEC guard against hijacking.

Defense-in-depth cheat sheet:
Poisoning → DNSSEC + port/0x20 randomization Amplification → RRL + BCP 38 + close open resolvers Eavesdropping → DoT / DoH / DoQ Zone transfer → TSIG Cert misissuance → CAA Tunneling → query analytics / DNS firewall
